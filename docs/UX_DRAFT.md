## 流れ

- 初回：ホーム → 対象確認 → デモログイン → 対象確認でUnlock → 準備中 → 結果。
- 再訪：ホームの最近の結果、またはMy Results → 結果。
- 取得失敗：準備中の「失敗時の表示を見る」→ 失敗説明 → 対象確認。
- アカウント設定はMy Resultsと分離。My Resultsはヘッダーから直接開く。
- ログイン前後でホームを共用し、ログイン後だけ最近の結果を表示。

## 2026-09-20: IO製品版への接続を実装

この節が現行の導線。通常の `/` は `/io` へ、旧 `/user/:username` と旧プロトタイプ結果URLは `/io/:username` へ転送する。
旧ログイン・新規登録・アカウント・My ResultsもIOページへ転送。旧ゲスト結果リンクは移行案内のみ表示し、旧取得を再開しない。

- 全体の認証は `IoSessionProvider` と `/api/io/auth/*` のIO専用Cookie。
- 検索後は上部プロフィール → Unlock → 旧結果画面の部品。ログイン後は検索対象へ戻る。
- プロフィール・本人の境界・取得状態・保存した期間はIO PostgreSQLから読み取る。
- 新規アカウントのプロフィールはまだDBにないためユーザー名のみ表示し、取得後に更新する。旧プロフィールAPIには戻らない。
- Unlockは `/api/io/unlocks/prefix`、期間指定は `/api/io/unlocks/range`。ユーザーの明示確認後だけ実行。
- 投稿・進捗APIのSQLite分岐を廃止。`STELA_IO_USE_POSTGRES=0`でもIO PostgreSQLとIO認証を使用する。
- 旧試作の取得開始 `/api/io/runs` POSTは410。ユーザー向けUIから呼ばない。
- My ResultsはIO側の本人のUnlock・期間権限・ジョブ履歴。保存済み結果のViewでは新規取得をしない。
- 取得ワーカーはWebとは別プロセス。確認時点ではIO専用DBにワーカーロックはなかった。

### ローカル起動

Web: `npm run dev`

別ターミナルで取得ワーカー: `npm run io:worker:local`

ローカルワーカーはNextと同じ優先順位で環境ファイルを読み込む。IO専用DBのdirect URLとAPIキーが必要。
ワーカーはそのDBの取得待ちジョブを処理するため、起動すると外部APIを使用し得る。
